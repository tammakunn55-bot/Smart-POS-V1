# v11 — ล็อกอินรายพนักงาน + ที่เก็บข้อมูล IndexedDB

## ล็อกอินรายพนักงาน
| ก่อน | หลัง |
|---|---|
| ทุกเครื่องล็อกอิน Supabase ด้วยบัญชีเจ้าของร้านบัญชีเดียว (PIN เป็นด่านฝั่งเครื่อง) RLS แยกบทบาทไม่มีผลจริง | พนักงานแต่ละคนมี Supabase session ของตัวเอง ได้จาก Edge Function `pin-login` (ตรวจ PIN ฝั่งเซิร์ฟเวอร์, PBKDF2/SHA-256, พักล็อกอินหลังผิด 5 ครั้ง 30 วิ→15 นาที, สร้างบัญชี Auth ให้อัตโนมัติครั้งแรก) |
| บิลระบุ `user_id` ใครก็ได้ | trigger `guard_bill_user`: ผู้ที่ไม่ใช่ผู้จัดการบันทึกบิลได้เฉพาะในนามตัวเอง |
| ผู้จัดการแก้ `auth_user_id` ของพนักงานเพื่อสวมรอยได้ | trigger `guard_app_users_identity` ห้ามแก้ `auth_user_id`/`login_email` จากฝั่งผู้ใช้ |
| แคชเชียร์แก้วงเงินลูกค้าได้ | แคชเชียร์เพิ่มลูกค้าใหม่ได้ แก้ได้เฉพาะผู้จัดการ (RLS) และไม่ทับวงเงินตอนซิงค์ |
| ออฟไลน์แล้วล็อกอิน | ใช้งานในเครื่องได้ตามปกติ คิวค้างไว้; กลับมาออนไลน์ระบบล็อกอินเซิร์ฟเวอร์ให้อัตโนมัติ (PIN อยู่ในหน่วยความจำเท่านั้น ไม่เขียนดิสก์) |
| ล็อกเครื่อง/สลับพนักงาน | `signOut({scope:'local'})` — คนถัดไปต้องใส่ PIN ของตัวเอง |
- เป็นโหมดเลือกเปิด (`db.settings.perEmployeeAuth`) ปิดอยู่ = พฤติกรรม v10
- รายการในคิวมีฟิลด์ `by`; แคชเชียร์ส่งเฉพาะของตัวเอง งานผู้จัดการ (ปรับสต็อก/รับของ/ลบ) ข้ามไปรอผู้จัดการ
- แคชเชียร์ไม่ซิงค์แคตตาล็อกและไม่ดึงข้อมูลจากคลาวด์ (ไม่มีสิทธิ์อ่านต้นทุน/สต็อกทั้งหมด)

## ที่เก็บข้อมูล
| ก่อน | หลัง |
|---|---|
| ทั้งฐานข้อมูล `JSON.stringify` ลง localStorage ก้อนเดียว (~5MB, เขียนทั้งก้อนทุกครั้ง) | IndexedDB: meta 1 ระเบียน + บิลรายใบ, เขียน debounce 60ms, บิลเขียนเฉพาะที่เปลี่ยน (บิลเก่า >7 วันเขียนเมื่อถูก `touchBill`) |
| เต็มแล้วเงียบ/เตือนเมื่อพังแล้ว | แจ้งเตือนเมื่อเขียนไม่สำเร็จ + ขอ persistent storage + บันทึกทันทีเมื่อซ่อน/ปิดแท็บ |
| session Supabase ใน localStorage | เก็บใน IndexedDB (custom `auth.storage`) |
| — | ย้ายข้อมูลเดิมอัตโนมัติ (เก็บสำเนา `legacy_backup`), ถอยกลับ localStorage ถ้า IndexedDB ใช้ไม่ได้, แท็บที่สองอ่านอย่างเดียว |
- สคริปต์ของแอปเปลี่ยนเป็น `type="text/x-pos-app"` และถูกรันโดยตัวโหลดหลังอ่าน IndexedDB เสร็จ (ตัวโหลดเรียก DOMContentLoaded ที่แอปลงทะเบียนไว้ให้ย้อนหลัง)

## ยังไม่ได้ทำ / ข้อจำกัด
- ไม่ได้ทดสอบกับ Supabase/Deno จริง (ฟังก์ชัน `pin-login` ทดสอบ logic ผ่าน Node ด้วย deps จำลอง) · `0003` ยังไม่เคยรันบน Postgres จริง
- การล็อกอินใช้ magic-link token (`generateLink` + `verifyOtp`) — พฤติกรรมของ `type` อาจต่างตามเวอร์ชัน supabase-js/Auth
- ล็อกอินเซิร์ฟเวอร์ส่ง PIN ดิบผ่าน HTTPS ครั้งเดียวต่อการล็อกอิน (ไม่เก็บ) · ผู้โจมตีที่รู้ user_id ทำให้บัญชีถูกพักชั่วคราวได้ (ไม่มี rate-limit ระดับ IP)
- แคชเชียร์ที่เปลี่ยน/สร้าง PIN บนเครื่อง ต้องรอผู้จัดการซิงค์ก่อนจึงล็อกอินเซิร์ฟเวอร์ได้
- ยังไม่มีหน้าจอ UI สำหรับปลดล็อกพนักงาน (ใช้ SQL `unlock_staff`) และไม่มีการเพิกถอน session ทันทีเมื่อปิดใช้งานพนักงาน (แต่ `is_staff()` เช็ค `is_active` ทุกคำสั่ง จึงถูกปฏิเสธทันที)
- ข้อมูลเก่ายังเป็น base64 ในระเบียน meta ถ้ามีรูปฝังในสินค้า (ควรอัปโหลดขึ้น Storage)
